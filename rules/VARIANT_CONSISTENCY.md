# VARIANT_CONSISTENCY.md —— 跨版本经历/项目一致性（硬约束）

> 这是用户最看重的设计原则，优先级与 FACT_RULES.md 同级。

## 核心目标

**不是「为每个 JD 造一份 ATS 最高命中的简历」，而是「用最少、最一致、最真实的几个版本，覆盖大多数目标岗位，同时把面试准备成本压到最低」。**

联合优化：简历质量 + 市场覆盖 + 真实性 + 跨版本一致 + 面试准备效率。

## 1. 实习经历一致性

默认：7 个版本（CN/US × DA/BA/DS/AI Analytics）用**同一批实习**。

- 允许不同：bullet 选择、bullet 顺序、措辞、侧重点、支持的术语。
- 不允许：换经历、改事实、改方法、改数据量、改结果、编造建模/实验/业务影响。

各角色侧重点：

| 角色 | 强调 |
|---|---|
| DA | SQL、Python、KPI 监控、Dashboard、下钻、根因分析、数据管道 |
| BA | 业务驱动、市场/用户洞察、建议、策略、决策支持 |
| DS | 统计、实验、量化方法、建模（**仅当证据真实支持**） |
| AI Analytics | 分析自动化、AI 辅助分析、智能工作流（**仅当真实做过**） |

## 2. 小核心项目库（SMALL CORE PROJECT BANK）

维护 **3–4 个**核心项目（不是大量项目）。选择标准：

1. 能同时支撑多个角色方向（DA/BA/DS/AI）
2. 证据强度高
3. 量化/业务/技术深度足
4. 面试讲得好
5. 与实习经历互补
6. 含高频市场技能
7. **最后**才考虑单个 JD 的边际关键词优势

## 3. 每份简历 2–3 个项目

- **实习**：3 个全用、完全一致（就这 3 个）。
- **项目**：每份简历选 **2–3 个**，选**最适配该方向**的（关键词 / 方法 / 业务最匹配）；但**尽量保持部分重叠**——不要每份简历的项目组完全不一样。理想：几个方向共用一两个核心项目，再各补方向专属的。

## 4. 项目切换阈值

- 不因「多一两个关键词」换项目。
- 换项目必须是**实质性提升**。推荐换之前必须写清：
  - Current Project / Alternative Project
  - 为什么替代品实质性更强
  - 覆盖了什么重要角色要求
  - 为什么改写现有项目措辞不够
- 没有强理由 → **不换**。

## 5. 同一项目、不同定位（首选策略）

**同项目 → 不同角色化描述**，而不是**不同角色 → 完全不同项目**。

事实完全一致；只改 framing（bullet 选择/顺序/措辞/强调/术语/角色相关框架）。

## 6. 项目表示层（Representation Layer）

每个核心项目维护：

```
project_x/
  source_of_truth.md            # 唯一事实
  DA_representation.md          # 都是同一项目的真实表示
  BA_representation.md
  DS_representation.md
  AI_Analytics_representation.md
```

这些**不是不同项目**，是同一项目的不同真实表示，必须指向同一份 verified evidence。

## 7. 面试准备成本（显式优化因子）

- 每多引入一个活跃项目，准备成本增加。
- 除非其招聘价值明显超过额外准备成本，否则不推荐新增。
- 偏好 **3 个吃透的项目** 而非 **8 个半吊子项目**。

## 8. 最终项目策略报告（交付物）

分析完 JD 库 + 项目证据后，产出：

- CORE PROJECT #1–#4（每个说明：为何入选、支撑哪些角色、最强技能/方法、面试价值、证据强度）
- DEFAULT 两个项目（大多数简历上用哪两个）

示例结构（示意，实际按方向选最优、保持重叠）：

```
CN_DA:    Project A + B + C
CN_BA:    Project A + B + D
CN_DS:    Project A + C + D
CN_AI:    Project B + C + E
```

> 实习全部一致；项目每份 2–3 个、按方向选最适配的，但共用若干核心项目、不完全换一遍。
